# dsh-inbox · 个人「信息聚合中心」可行性调研与设计方案

> 版本：v0.1（调研稿，未开始编码）
> 目标：把个人邮箱（Gmail / QQ邮箱）、QQ 消息、微信消息、抖音消息聚合到 DSH 的一个面板里，统一收发/查看。
> 结论先行：**邮箱部分完全可行且合规；QQ 消息可行但走非官方协议、有账号风险；微信/抖音个人号官方无接口，只能走 Hook/RPA，风险高、稳定性差，建议做成可选且免责的插件。**

---

## 1. 目标与范围

| 维度 | 说明 |
|---|---|
| 用户 | 单个自然人（非企业） |
| 渠道 | Gmail、QQ邮箱（收/发邮件）；QQ 消息、微信消息、抖音消息（收/发即时消息） |
| 形态 | DSH 插件（Electron 宿主半侧 + Web GUI 前端半侧） |
| 核心价值 | 一个统一收件箱：跨渠道列表、未读数、搜索、按渠道/账号筛选，点开看详情；能回则回 |
| 非目标 | 企业级客服、群发营销、多租户 SaaS |

---

## 2. 可行性矩阵（结论速览）

| 渠道 | 官方接口 | 推荐接入方式 | 可行性 | 账号风险 | 稳定性 | 建议阶段 |
|---|---|---|---|---|---|---|
| **Gmail** | ✅ Gmail API / IMAP | IMAP（应用专用密码）或 OAuth2+XOAUTH2 | ★★★★★ | 无（合规） | 高 | **P0 必做** |
| **QQ邮箱** | ✅ IMAP/SMTP | IMAP + 16 位授权码 | ★★★★★ | 无（合规） | 高 | **P0 必做** |
| **QQ 消息** | ❌ 无个人接口 | NapCat / LLOneBot（OneBot 11，跑独立 QQ 号） | ★★★☆☆ | 中高（可能冻结） | 中 | **P1 可选** |
| **微信消息** | ❌ 无个人接口 | WeChatFerry/PadLocal Hook 或 RPA | ★★☆☆☆ | 高（易封号） | 低（版本锁死） | **P2 可选+免责** |
| **抖音消息** | ⚠️ 仅企业号/小程序客服 | 抖音开放平台 IM（企业）或 RPA 浏览器扩展 | ★★☆☆☆ | 中（个人号用到 RPA） | 中低 | **P2 可选** |

> 一句话：**能干净做完的是「邮箱聚合」；即时消息三家都是灰色地带，能不能长期用取决于平台风控，不能向用户承诺稳定。**

## 3. 各渠道可行性详解

### 3.1 Gmail（★★★★★，合规）

- **官方 Gmail API**（OAuth2）：能读邮件、读线程、发信、改已读/标签，最规范；缺点是 OAuth 流程（桌面 App 需 loopback 回调）和 Google Cloud 项目配置稍重。
- **IMAP + 应用专用密码**：邮箱账号开启两步验证后生成 App Password，用 IMAP 直接收信，SMTP 发信。实现最简单，**推荐 MVP 先用它**，后续再加 OAuth。
- 发送：SMTP（smtp.gmail.com:465/587）。
- 结论：可行、稳定、合法。

### 3.2 QQ 邮箱（★★★★★，合规）

- 官方支持 **IMAP / SMTP**，但默认关闭，需要在 QQ邮箱网页版「设置 → 账号与安全 → POP3/IMAP/SMTP 服务」里开启，并通过短信验证拿到 **16 位授权码**（不是 QQ 密码）。
- 配置：IMAP `imap.qq.com:993`（SSL），SMTP `smtp.qq.com:465`（SSL）。用户名填完整邮箱，密码填授权码。
- 特殊点：QQ邮箱 IMAP 对 `ID` 命令有要求，部分客户端需先发 `ID ("name" "xxx")`，`imapflow` 一般能处理；收件箱文件夹名是中文（如「收件箱」）。
- 结论：可行、稳定、合法。

### 3.3 QQ 消息（★★★☆☆，非官方）

- 腾讯**没有**给个人 QQ 开放消息 API。生态里的做法是：用一个「机器人 QQ 号」登录 **NapCat / LLOneBot**（基于 NTQQ 的 OneBot 11 实现），对外暴露 HTTP / WebSocket，任何程序通过 OneBot 协议收发消息。
- 能力：收群消息/私聊、发消息、拿好友/群列表、收图片文件。对本项目够用。
- 代价与风险：
  - 要把一个 QQ 号当成「机器人」长期在线，**可能被腾讯风控冻结**（尤其是新号/异地/高频）。
  - 需要额外部署一个 NapCat 进程（Docker 或 Windows 版），插件只是它的客户端。
  - 协议随 QQ 客户端版本变化，需跟随社区更新。
- 结论：技术上可行，适合「自用、能接受掉线/冻结风险」的用户；**不建议作为默认开启项**。

### 3.4 微信消息（★★☆☆☆，高风险）

- 微信**官方只开放企业微信（WeCom）和公众号/小程序**接口，**个人微信号没有官方消息 API**。
- 现实中的三条路：
  1. **Hook 类**（WeChatFerry / wcferry，注入 PC 微信 DLL）：能力最强（收发文字/图片/文件、群），但**强绑定某个微信 Windows 版本**，微信一升级就失效，且**违反用户协议、封号风险高**。
  2. **PadLocal 类**（Wechaty + padlocal 付费 token）：基于 iPad 协议，相对稳定但要付费、也有封号案例。
  3. **RPA 类**（UI 自动化 / 无障碍 / 浏览器扩展）：不碰协议、最「合规擦边」，但慢、易被 UI 改动打断、只适合轻量自动回复。
- 结论：**没有稳妥的官方方案**。若要做，必须做成「用户自行承担风险」的可选适配器，并在 README 明确免责。

### 3.5 抖音消息（★★☆☆☆，受限）

- 抖音开放平台有 **IM 消息能力**，但面向**小程序 / 企业号（蓝V）客服会话**，不是普通个人号的私信收件箱，需要企业资质和审核。
- 个人号私信没有任何官方读取接口。可行路线只剩 **RPA（浏览器自动化 / 扩展）**，例如开源社区用浏览器扩展做「非破解协议」的私信自动回复。
- 结论：**个人号几乎只能 RPA**，稳定性和合规都一般；企业场景可走开放平台。建议放到最后或先不做。

## 4. 关键风险与合规

1. **账号安全**：微信/QQ/抖音的 Hook 与协议方案可能触发风控、封号、冻结。必须在 UI 与文档里显著提示，默认关闭，由用户显式开启。
2. **凭据安全**：邮箱授权码、OAuth token、Bot token 属于高敏感信息。**只能存本机 `DSH_HOME`**，加密存储，绝不入 Git、绝不写日志。
3. **法律/协议**：Hook 类方案可能违反平台用户协议；本插件定位「个人自用工具」，不对外提供破解，不批量抓取。
4. **稳定性预期管理**：非官方渠道随时可能失效，UI 要有「连接健康状态/最近错误」展示，不能让用户以为一直可用。
5. **数据出境/隐私**：邮件内容本地存储；若接第三方云（PadLocal 等）需明示数据会经过第三方。

## 5. 总体架构设计

### 5.1 分层（沿用 DSH 插件两半侧）

```
┌─────────────────────────── DSH Web GUI (浏览器半侧 lib/client.js) ───────────────────────────┐
│  sidebar.panellist「信息中心」入口                                                             │
│  main 面板：统一收件箱 UI                                                                     │
│    - 顶部：渠道 Tab(全部/邮箱/QQ/微信/抖音) + 账号筛选 + 搜索框 + 未读统计                     │
│    - 左列：会话/邮件列表（未读点、渠道色标、时间）                                             │
│    - 右列：详情（正文/附件/图片，能回则显示回复框）                                            │
│    - 设置页：账号与凭据、连接健康、开关渠道                                                    │
│         │ fetch('api/dsh-inbox/...')  （相对路径，IPC 承载）                                   │
└─────────┼───────────────────────────────────────────────────────────────────────────────────┘
          ▼
┌─────────────────────────── DSH 宿主 (lib/index.js, Node/Electron) ───────────────────────────┐
│  HTTP 路由层  /api/dsh-inbox/state | /api/dsh-inbox/accounts | /api/dsh-inbox/send          │
│  聚合服务     Aggregator：多 adapter 汇总、去重、排序、未读、搜索                             │
│  调度器       Scheduler：每 N 秒/每 adapter 节奏触发 pull，增量游标                           │
│  存储         Store：DSH_HOME/dsh-inbox/*.json（原子写+备份），凭据单独加密文件               │
│  适配器(Connector)                                                                             │
│    ├─ GmailConnector   (IMAP / SMTP 或 Gmail API)                                             │
│    ├─ QQMailConnector  (IMAP / SMTP)                                                          │
│    ├─ QQConnector      (OneBot 11 → NapCat HTTP/WS)                                           │
│    ├─ WeChatConnector  (WeChatFerry / RPA，可选)                                              │
│    └─ DouyinConnector  (开放平台/RPA，可选)                                                   │
└───────────────────────────────────────────────────────────────────────────────────────────────┘
          │
          ▼ 外部依赖（用户自备）
   Gmail/QQ邮箱 SMTP·IMAP 服务器 │ NapCat 本地进程 │ WeChatFerry 本地进程 │ 抖音 RPA/开放平台
```

设计要点：
- **适配器模式（Adapter）**：每个渠道实现统一的 `Connector` 接口，聚合层不关心底层协议。新增渠道 = 加一个 adapter 文件。
- **不把协议逻辑塞进宿主**：QQ/微信/抖音的连接都指向用户本机已跑起来的服务（NapCat / WCF / RPA），插件只做 HTTP/WS 客户端，降低耦合与升级负担。
- **邮箱走标准协议**：直接用 `imapflow` + `nodemailer`，不需要每个平台单独对接。

### 5.2 统一消息数据模型

```js
// 归一化后的消息
{
  id: "qqmail:me@qq.com:uid-12345",   // 全局唯一：channel:accountId:nativeId
  channel: "qqmail",                   // gmail | qqmail | qq | wechat | douyin
  accountId: "me@qq.com",              // 对应账号
  conversationId: "thread-abc",        // 会话/邮件线程 id
  conversationName: "张三",             // 列表显示名
  conversationAvatar: null,
  direction: "in",                     // in | out
  senderName: "张三",
  type: "text",                        // text | image | file | audio | video | link | system
  text: "在吗？",
  attachments: [{ name: "a.pdf", mime: "application/pdf", size: 12345, path: "..." }],
  ts: 1761700000000,                   // epoch ms，统一时间
  unread: true,
  raw: { /* 原始报文，调试用，可截断 */ }
}
```

```js
// 会话摘要（列表用）
{ conversationId, channel, accountId, name, lastText, lastTs, unreadCount, avatar }
```

### 5.3 Connector 接口（宿主侧约束）

```js
/**
 * @typedef {Object} Connector
 * @property {string} channel
 * @property {number} pollIntervalMs
 * @property {(config) => Promise<void>} init        // 校验凭据，建立连接
 * @property {() => Promise<{ok:boolean, detail:string}>} healthCheck
 * @property {(cursor) => Promise<{messages, nextCursor}>} pull  // 增量拉取
 * @property {(msg) => Promise<{ok:boolean}>} [send]           // 可选：发送/回复
 * @property {() => Promise<void>} [dispose]
 */
```

- `pull(cursor)` 只返回「上次游标之后」的新消息，游标由各 adapter 自己定义（IMAP 用 UIDVALIDITY+UID，OneBot 用内存事件队列，RPA 用时间戳）。
- 聚合层负责：调用所有已启用 adapter 的 `pull` → 归一化 → 按 `id` 去重 → 落库 → 更新未读。

### 5.4 拉取 / 推送策略

- **MVP 用轮询**：宿主 `setInterval` 按 adapter 各自节奏拉取；前端每 3–5 秒 `POST api/dsh-inbox/state {op:'list'}` 取快照。
- **增强（可选）**：DSH 有 `dsh-api-gateway` 的事件转发能力，可让宿主在拉到新消息时主动 push 给前端，减少轮询；但实现复杂，放 P1。
- **增量与限流**：IMAP 用 `UID > lastUid` 增量；首次同步只拉最近 N 天 / N 封，避免一次拉爆。

### 5.5 存储设计

- 位置：`%DSH_HOME%/dsh-inbox/`
  - `messages.json`：归一化消息（按账号分片或单文件，限制每账号保留最近 ~2000 条，滚动淘汰）
  - `accounts.json`：账号配置（不含明文密钥）
  - `secrets.bin`：加密后的凭据（见 §7）
  - `cursors.json`：各 adapter 增量游标
  - `backups/`：最近 20 份自动备份（沿用 todolist 的备份策略）
- 原子写：写 `.tmp` 再 `rename`；读取时主文件损坏自动回退备份。
- **升级路径**：数据量大时再换 SQLite（`better-sqlite3` 是原生模块，Electron 需 rebuild，MVP 不用，先用 JSON）。

### 5.6 UI 设计（复用 dsh-todolist 视觉语言）

- 左导航：图标 + 「信息中心」，`order` 放在 dsh-context(20) 之后，例如 40。
- 主面板三栏/两栏：
  - 顶部工具条：渠道 Tab（全部 / 邮箱 / QQ / 微信 / 抖音）、账号下拉、搜索、全部已读、刷新。
  - 会话列表：未读圆点、渠道色条、名称、最后一条摘要、相对时间。
  - 详情区：邮件显示主题/发件人/正文（HTML 需安全净化）/附件下载；IM 显示气泡。
  - 底部/右侧：回复框（仅对支持 send 的渠道显示）。
- 设置页：每个账号一张卡——登录状态、健康灯、上次同步时间、重新授权/断开。
- 空态/错误态：明确提示「未配置账号」或「NapCat 未连接」及修复步骤。

## 6. 分阶段实施路线

### P0 — 邮箱聚合 MVP（建议先做，1.5–2.5 天）
- 插件骨架（package.json / cordis.patch.yml / index.js / client.js / install.ps1）。
- `GmailConnector` + `QQMailConnector`（IMAP 收、SMTP 发，应用专用密码/授权码）。
- 统一收件箱 UI（列表 + 详情 + 搜索 + 未读 + 手动刷新）。
- 账号配置与加密存储、离线单测（mock IMAP）。
- **交付即有价值、完全合规**，先把架构与 UI 打磨好。

### P1 — QQ 消息（1–2 天）
- `QQConnector`：连 NapCat 的 OneBot HTTP（够用）或 WebSocket（实时）。
- 收私聊/群消息、发消息、会话合并。
- 设置页加「NapCat 地址 / token」与连接健康检查。

### P2 — 微信 / 抖音（各 1–2 天，可选、免责）
- `WeChatConnector`：优先对接用户自备的 WeChatFerry HTTP 服务（不内置 hook 代码）。
- `DouyinConnector`：优先 RPA/浏览器扩展桥，或企业开放平台（若有资质）。
- 默认关闭，README 显著免责，UI 标红风险提示。

> 若只做 P0+P1，就是一个「邮箱 + QQ」的实用聚合中心；微信/抖音按需再加。

## 7. 安全与隐私

1. **凭据加密**：优先用 Electron `safeStorage`（Windows 下走 DPAPI，绑定当前用户）；取不到时退化为 AES-256-GCM，密钥由「机器标识 + 用户」派生并存于受限 ACL 文件。**绝不写入日志、绝不提交仓库。**
2. **HTML 邮件净化**：邮件正文是 HTML，必须 sanitize（去 script/iframe/远程图片默认不加载），防 XSS。
3. **本地优先**：消息与凭据只落本机 `DSH_HOME`；远程仅访问各平台官方服务器/用户自备本地服务。
4. **权限最小化**：邮箱用应用专用密码/授权码，不用主密码；Gmail OAuth 只申请只读或 gmail.modify 最小范围。
5. **免责声明**：非官方渠道（QQ/微信/抖音）在 README.zh/en 与 UI 中明确「可能违反平台协议、存在封号风险，用户自行承担」。

## 8. 依赖选型

| 用途 | 选型 | 说明 |
|---|---|---|
| IMAP 收信 | `imapflow` | 现代、Promise、支持 XOAUTH2，纯 JS |
| 邮件解析 | `mailparser` | MIME/附件/HTML 解析，纯 JS |
| SMTP 发信 | `nodemailer` | 成熟稳定，纯 JS |
| OneBot 客户端 | 内置 `fetch` / `ws` | HTTP 轮询够用；实时再上 `ws` |
| UI | React（基座）+ 手写 CSS | 无需构建，沿用 todolist 方式 |
| 存储 | Node `fs` + JSON | MVP 不引原生模块 |
| 加密 | Electron `safeStorage` / Node `crypto` | 见 §7 |

> 注意：插件依赖需在 profile 的 `node_modules/<pkg>` 下可解析；安装脚本里需 `npm install --omit=dev` 或把依赖随包复制。原生模块（如 better-sqlite3）在 Electron 里要 rebuild，MVP 刻意避开。

## 10. 待确认事项（决定下一步怎么走）

1. **渠道范围**：先只做「邮箱（Gmail+QQ）」的合规 MVP，还是一开始就要把 QQ 消息也接上？
2. **风险偏好**：微信 / 抖音个人号只能走 Hook/RPA，是否接受（默认关闭 + 免责）？还是这两家先不做？

4. **邮箱鉴权**：用最简单的「应用专用密码 / 授权码」（快），还是做「Gmail OAuth2」（更正规但要配 Google Cloud）？
